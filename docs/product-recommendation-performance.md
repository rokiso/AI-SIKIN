# 화장품 추천 API 성능 회귀 수정

2026-11-19 (한국 시간), ign8t `9e57c21d-aef7-4c48-a6d4-3cd7fcb29f45`의 성능 보완. 기준 커밋 `bc98c1f`.

## 문제와 원인

기존 로컬 DB 검사에서 `GET /api/v1/catalog/products/recommendations`의 50개 동시 warm 요청 p95가 300ms 기준을 넘었다. 직전 작업의 수정 전 worktree `50caf06`에서도 약 531ms로 재현됐으며 이번 작업 시작 시 545.7ms를 확인했다.

계측한 재현에서는 p95 723.8ms, 쓰기 트랜잭션 50회였다. 매번 같은 추천 목록이어도 트랜잭션을 시작하고 같은 리포트의 advisory lock을 순서대로 획득한 뒤 내용이 같은지 확인했다. 이를 생략하는 읽기 경로만 추가했을 때는 457.4ms로 여전히 실패했다. 같은 제품·성분 규칙을 읽고 같은 추천을 계산하는 중복 작업도 DB 연결과 CPU를 사용했다. 임시 구간 계측에서도 성분 규칙 조회/처리와 매핑 조회의 대기가 확인됐다. 임시 계측 코드는 최종 구현에 남기지 않았다.

## 변경과 보호 범위

- 요청마다 기존 실제 세션 조회 및 리포트 소유권 검증을 먼저 수행한다. 같은 리포트라는 이유만으로 인증/소유권 검증 전에 계산에 합류하지 않는다.
- 인가된 동일 리포트·입력·제품 revision의 진행 중인 계산만 공유한다. 성공/실패 시 제거하며 완료된 개인 응답을 캐시하지 않는다. 외부 캐시·새 DB 테이블·새 의존성은 추가하지 않았다.
- 인가 후 독립적인 공개 제품/성분 규칙/기존 매핑 조회를 함께 진행한다. 기존 제품의 30초 캐시만 유지하고, 성분 규칙은 다음 계산 때 다시 읽는다.
- 기존 매핑이 같으면 쓰기 트랜잭션을 시작하지 않는다. 다르면 기존 DB 잠금 안에서 다시 확인하고 삭제/생성을 원자적으로 처리한다. 다른 프로세스의 동시 생성 보호도 이 잠금/고유 제약을 계속 사용한다.
- 추천 사유와 대상 성분도 비교해 상품 ID가 같은 경우의 낡은 매핑 메타데이터를 보정한다. 구매 중계의 최신 상품 상태·허용 URL·원자적 클릭 기록·탈퇴와의 잠금은 변경하지 않았다.

추천 API 성능이 좋아져도 운영 상품/제휴 계약 검증이나 개인별 의학적 적합성 검증을 완료한 것은 아니다. 실제 카탈로그 기본 잠금과 체험 안내를 유지한다. 운영 DB·환경·공개 배포·Git push는 변경하지 않았다.

## 검증

- 기존 성능 검사의 **50개 요청과 p95 <300ms 기준을 유지**했다. 수정 후 관련 테스트 파일에서 279.4ms, 전체 DB 실행에서 **168.8ms**로 통과했다. 테스트 실행 환경 부하에 따른 변동이 있으며 운영 네트워크/SLA 수치로 일반화하지 않는다.
- 성능 검사에서 실제 세션 조회 50회, 리포트 조회 50회, warm 쓰기 트랜잭션 0회를 함께 검증한다. 최초 5개 동시 생성 후 8개 매핑도 그대로 검증한다.
- 계산을 의도적으로 대기시킨 동안 타인의 소유권 및 철회된 세션 요청이 404인지 확인했다. 다른 리포트가 섞이지 않고, 실패한 계산이 503을 반환한 뒤 다음 요청으로 복구되는지 확인했다.
- 완료된 계산 뒤 추천 사유/성분 메타데이터 변경을 복구하고, 제품 전성분 변경과 카탈로그 무효화 후 부적합 상품/매핑이 제외되는지 확인했다. 진단 리포트 불변 DB 보호는 해제하지 않았다.
- 정적 검사·단위·DB·빌드·관련 브라우저를 순서대로 실행해 성능 측정에 다른 테스트 작업이 겹치지 않도록 했다. 결과는 아래에 기록한다.
