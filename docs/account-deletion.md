## 선택 이유와 범위

현재 미구현된 회원 삭제는 개인정보 처리와 약관 활성화를 막는 선행 조건이다. 새 프로젝트/마스터/다음 작업을 순서대로 조회했고, 마스터가 이전에 읽은 버전과 같고 작업 스펙이 ready이며 stale이 아님을 확인했다. 기존 OAuth·Prisma·비공개 S3 모듈·동의 이력·native dialog 패턴을 재사용했다. `UserConsentHistory`는 이미 구현되어 있으므로 중복 모델을 만들거나 기존 동의 계약을 변경하지 않았다.

- `DELETE /api/v1/users/me`: 같은 출처, DB로 검증한 회원 세션, 정확한 `confirmationPhrase: "탈퇴합니다"`, `agreedToDataLoss: true`만 허용한다. 추가 ID 필드도 거절한다. UUID 헤더를 소유권 증거로 사용하지 않는다.
- `GET /api/v1/users/me`: 로그인한 본인의 삭제 예정 진단·데일리 기록 수만 반환한다. 두 응답 모두 private/no-store.
- 마이페이지 회원에게만 탈퇴 진입 버튼이 보인다. 확인창에 조회 중/조회 실패·재조회, 빈 기록, 확인 입력, 삭제 중, 실패·재시도, 완료 상태를 제공한다. 오류에도 입력을 유지하고, 처리 중 중복 제출과 ESC·취소·닫기를 차단한다. 성공을 1초간 알린 뒤 홈을 전체 로드해 기존 회원 컨텍스트를 버린다.

## 처리 순서와 실패 의미

1. DB 트랜잭션에서 사용자 행을 `FOR UPDATE`로 잠그고 같은 토큰의 살아 있는 세션을 다시 확인한다. 다른 삭제와 신규 FK 기반 업로드·기록·동의·세션 생성을 직렬화한다. 감사 서명 설정과 감사 테이블 조회도 외부 삭제 전에 확인하여 새 마이그레이션이 빠진 환경에서 먼저 사진을 지우지 않는다.
2. 본인의 `ImageUploadSession`, `SnapshotUploadSession`, `DailySnapshot`을 모두 포함해 파일 키를 수집·중복 제거한다. 아직 타임라인에 없는 업로드도 빠뜨리지 않는다. 다른 계정 또는 비회원 기록과 객체가 공유된 비정상 상태는 409로 중단한다.
3. 업로드 상태가 UPLOADED여도 발급한 PUT URL은 다시 쓸 수 있다. 만료 시간 + 60초 여유가 지나기 전에는 409 `UPLOAD_LINK_STILL_VALID`로 중단한다. 최대 16분 후 재시도 안내를 한다.
4. 파일이 없으면 스토리지를 호출하지 않는다. 파일이 있으면 버킷 버전 설정을 확인한다. 버전 관리 Enabled/Suspended는 정확히 같은 키의 모든 버전과 delete marker를 페이지 끝까지 수집하고 VersionId를 지정해 삭제한다. Prefix가 같은 다른 객체는 지우지 않는다.
5. 삭제 요청은 최대 1,000개씩 나눈다. HTTP 성공만 믿지 않고 항목별 Errors와 Deleted 응답을 확인한다. 이후 버전 목록 또는 Prefix 제한 객체 목록로 잔존 여부를 다시 확인한다. 버전 조회·삭제 권한 부재, Object Lock·보존 정책, 불완전 응답, 잔존 객체, 타임아웃은 성공으로 처리하지 않는다. 전체 S3 작업은 15초, DB 트랜잭션은 30초 한도다.
6. 스토리지 확인 후 DB의 사용자·OAuth 계정·모든 세션·동의·업로드·스냅샷·진단·리포트·추천 종속 데이터를 CASCADE 삭제한다. FK가 없는 제휴 클릭과 진단에 연결된 AI 로그도 명시적으로 제거한다.
7. 감사 기록을 같은 트랜잭션에서 생성한다. 소유자 HMAC, 삭제 논리 키 수, 삭제 레코드 수, 완료 시각만 남기고 원본 userId·IP·사진 키·이메일은 남기지 않는다. HMAC은 기존 서버 서명 키에서 용도를 구분해 생성한다. 이를 완전 익명이라고 표현하지 않는다. 성공 응답에서 회원·게스트·OAuth·이관 안내 쿠키를 만료시킨다.

S3와 PostgreSQL은 분산 트랜잭션을 공유하지 않는다. S3 다중 삭제도 원자적이지 않다. **S3 일부 삭제 뒤 실패하거나 S3 성공 뒤 DB 커밋이 실패하면 이미 삭제한 사진을 되돌릴 수 없다.** DB는 롤백되어 계정과 파일 키가 남으므로 재로그인/재시도로 같은 삭제를 이어갈 수 있다. 502/503과 확인창은 이 부분 실패를 명시하고 완료로 표시하지 않는다. 영구적인 자동 재시도 워커나 운영 스케줄을 배포했다고 주장하지 않는다.

늦은 요청의 식별자 재생성을 막기 위해 제휴 클릭 저장은 사용자 행 KEY SHARE 잠금과 존재 확인을 사용한다. 진단에 연결된 AI 로그도 진단 행의 KEY SHARE 잠금으로 삭제와 직렬화한다. 진단이 이미 지워졌으면 sessionId 없이 기존의 제한된 제공자·지연·토큰 메타데이터만 남긴다. 사용자와 연결되지 않은 기존 시스템 통계 로그를 임의로 삭제하지 않는다.

## 스펙 조정

- S3 Batch Delete를 원자적 영구 삭제로 간주하지 않는다. 버전 삭제와 결과 재확인을 추가하고 부분 실패를 사실대로 보여 준다.
- 비식별 로그라는 설명과 원본 `requestedIp` 저장 요구는 충돌한다. IP는 수집하지 않았다. HMAC은 가명 정보로 취급한다.
- 발급된 업로드 URL의 재사용 때문에 모든 탈퇴가 즉시 완료된다는 약속은 할 수 없다. 살아 있는 링크가 있으면 삭제를 시작하지 않고 재시도를 안내한다.
- 새 스키마는 감사 테이블 1개뿐이다. 적용된 기존 마이그레이션·동의 구조·약관 활성 상태는 변경하지 않았다. 신규 마이그레이션은 검증된 폐기 가능한 로컬 DB에만 적용했다.
