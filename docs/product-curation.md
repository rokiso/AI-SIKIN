# 맞춤 화장품 큐레이션과 제휴 링크 중계

## 현재 구현 범위

기존 Product와 ProductRecommendation을 확장했습니다. DB 컬럼 brand/name/target_types/affiliate_url/match_reason과 카테고리 SERUM/SUNCARE는 그대로 유지하고 Prisma/API 표기를 스펙에 맞췄습니다. API에는 AMPOULE/SUNSCREEN으로 투영합니다. 새 마이그레이션은 `20261115010000_product_curation`이며 **로컬 DB에만 적용**했습니다. 적용된 이전 마이그레이션이나 운영 DB를 변경하지 않았습니다. 공개 배포에서는 쇼핑 체험 모드만 기본으로 열며, 실제 추천·구매 연결은 별도 활성화가 필요합니다.

실제 상품 32개를 검증한 상태가 아닙니다. 32개 가상·비활성 개발 샘플로 16개 피부 코드 × 4개 카테고리의 주력·대체 매핑을 검증했습니다. `ALLOW_SAMPLE_SEED=true npm run db:seed`는 검증된 로컬 DB에서만 동작하며 기존 ID의 데이터를 덮어쓰지 않습니다. 실제 상품·전성분·이미지 사용권·재고와 제휴 계약/계정은 별도 검증·등록이 필요합니다. 판매처나 상품 링크를 임의로 만들어 공개하지 않습니다.

## 추천 및 화면

- `/catalog/products?reportId=<UUID>`: 토너·앰플·크림·자외선 차단제 탭, 주력/대체 상품, 성분 기준 사유, 로딩·오류 재시도·빈 상태와 고지 문구.
- 홈의 기존 리포트 카드에서 ‘내 성분에 맞는 화장품 보기’로 진입합니다. 아직 별도 리포트 상세 화면이 없어 복구 링크는 실제 홈 리포트로 이동합니다.
- 리포트 없이 진입하면 제품을 임의 추천하지 않고 리포트 안내를 표시합니다. 사진 테스트 모드는 진단 리포트를 만들지 않습니다.
- 활성 제품 중 타입 태그와 추천 성분을 대조하고 주의 성분이 포함된 제품을 제외합니다. 성분 비교는 NFKC·공백·대소문자 정규화 후 텍스트 매칭이며, 성분 별칭 사전이나 임상 적합성 판정이 아닙니다. 전성분 입력 품질을 검토해야 합니다.
- 추천 사유는 중립적인 고정 문장에 성분명만 넣으며 치료·완치·재생 등 오인 표현을 걸러냅니다. 제품 원문·표시광고 전체에 대한 법률 검토를 대체하지 않습니다.
- 검토된 `/catalog-assets/*.webp` 로컬 파일만 제품 이미지로 사용합니다. 이미지가 없으면 제품 아이콘을 표시합니다. 제3자 이미지 서버를 호출하지 않습니다.

## API와 접근 제어

`GET /api/v1/catalog/products/recommendations?reportId=<UUID>`는 검증된 회원 또는 서명 증명이 있는 게스트의 **본인 완료 리포트**만 반환합니다. 익명·타인·만료/철회 세션·귀속 이전 후 게스트는 동일한 안전한 404를 받습니다. 스펙의 ‘리포트 ID만 유효하면 공개 조회’ 문구는 프로젝트의 항상 적용되는 서버 인가 규칙에 따라 강화했습니다. 잘못된/중복/추가 쿼리는 400입니다. 응답은 private,no-store입니다.

제품만 최대 2048개·30초 동안 프로세스 내 캐시하며 개인 리포트나 권한 판단은 캐시하지 않습니다. 실제 상품 등록·수정 경로에서는 `invalidateProductCache()`를 호출해야 합니다. 여러 인스턴스는 각자 TTL을 갖습니다. 리포트별 추천 생성은 트랜잭션과 advisory lock/고유 제약으로 동시성 중복을 막습니다.

2026-11-19 성능 보완: 같은 리포트의 **진행 중인 계산**만 합칩니다. 각 호출에서 먼저 실제 리포트 소유권을 조회하며, API의 세션 인증도 매번 수행합니다. 공유 키는 리포트 ID·타입·성분 입력·제품 카탈로그 revision으로 구분합니다. 계산이 끝나거나 실패하면 `finally`에서 제거하므로 완료 결과나 권한을 TTL 캐시하지 않습니다. 다른 프로세스 사이의 공유 캐시는 아닙니다. 성분 규칙 조회에도 새 TTL 캐시를 추가하지 않았습니다.

인가 후 서로 독립적인 제품·성분 규칙·현재 추천 매핑을 함께 읽습니다. 추천 매핑이 이미 같으면 쓰기 트랜잭션을 생략합니다. 생성/변경이 필요할 때는 기존 리포트별 DB 잠금을 획득하고 다시 확인한 뒤 원자적으로 갱신하므로 서로 다른 인스턴스의 최초 생성도 기존 방식으로 보호합니다. 매핑 비교에는 상품·카테고리·티어뿐 아니라 추천 사유와 대상 성분도 포함해, 상품이 같아도 오래된 설명을 그대로 남기지 않습니다. 제품 상태는 구매 중계에서 계속 최신 DB 값으로 검증합니다.

성능 보완의 재현·검증 기록은 [추천 API 성능 회귀 수정](./product-recommendation-performance.md)에 정리했습니다. 기존 전체 DB 검사에서 실패하던 50개 동시 요청 기준을 완화하지 않고 재검증합니다.

`GET /api/v1/catalog/redirect?productId=<UUID>&reportId=<UUID>&tier=PRIMARY|SECONDARY`는 선택적 리포트의 소유권과 실제 매핑을 확인합니다. 리포트 없는 공개 상품 링크도 지원하지만 개인 리포트 정보는 읽지 않습니다. 상품의 실제 최신 상태를 DB에서 확인하고 품절/비활성이면 같은 리포트·카테고리의 대체 상품을 사용합니다. 대체 상품도 없으면 내부 오류 페이지로 이동합니다.

검토된 상품 URL의 호스트를 서버 환경 `CATALOG_AFFILIATE_HOSTS`에 정확히 등록해야 합니다. HTTPS·허용 호스트만 지원하며 사용자 지정 URL/내부 주소/자격 증명/별도 포트는 거절합니다. 구매 링크를 표시하기 전에도 이 설정을 확인합니다. 허용 목록은 제휴 가입이나 정산용 ID를 대신하지 않습니다. 실제 제휴 계약에서 받은 기본 URL과 파라미터를 등록해야 합니다.

클릭 시 UUID를 발급하고 최종 URL을 포함한 로그 한 건을 트랜잭션으로 기록한 뒤 HTTP 302를 반환합니다. 실패하면 외부로 이동하지 않습니다. `utm_source=aiskin`, `utm_medium=recommendation`, `utm_campaign=report_curation`, `click_id`를 넣고 기존 제휴 파라미터를 보존합니다. 피부 타입·리포트 ID·사용자 ID·게스트 증명은 판매처에 넣지 않고 Referrer-Policy:no-referrer를 사용합니다. IP·Referer는 수집하지 않고 User-Agent는 제어문자를 제거해 512자로 제한합니다. 로그의 사용자/리포트/게스트 식별자에 관한 운영 보관·삭제 정책은 실제 출시 전에 확정해야 합니다.

## 링크 점검

로컬에서는 `npm run catalog:check`로 직접 점검할 수 있습니다. 운영용 `POST /api/v1/catalog/health-check`는 서버의 `CRON_SECRET_TOKEN`과 일치하는 Bearer 토큰을 요구하며, 인증된 호출을 DB 기준 분당 2회로 제한합니다. 본문을 생략하거나 JSON에 `dryRun`, `targetProductId`(UUID)를 넘길 수 있습니다. 드라이런은 승인된 링크를 점검하고 집계를 반환하며 상품 상태나 감사 이력은 기록하지 않습니다.

하루 한 번 한국 시간 오전 4시 20분에 호출하도록 GitHub Actions 워크플로를 추가했습니다. 배포 DB에 새 마이그레이션을 적용하고, 서버 및 GitHub Actions 시크릿에 같은 토큰을 설정한 뒤 GitHub Actions 변수 `CATALOG_HEALTH_CHECK_URL`에 배포된 엔드포인트 전체 HTTPS 주소를 설정하면 예약 실행이 시작됩니다. 호출이 모두 끝날 때까지 연결을 유지하는 서버에서 실행해야 합니다. 운영 배포·시크릿·예약 실행은 이 작업에서 설정하지 않았습니다.

링크는 최대 5개씩, HEAD와 필요한 경우 본문을 읽지 않는 GET을 사용해 URL별 5초 이내 점검합니다. 각 이동 단계의 허용 호스트를 검사하고 DNS가 반환한 공개 주소를 소켓에 고정합니다. 확인된 접속 실패는 상품 상태를 `UNAVAILABLE`로 전환하고, 이미 승인되었으며 카테고리·피부 타입·성분 조건을 갖춘 대체 후보를 점검합니다. 기존 추천의 주력/대체 계약에 따라 사용할 수 있는 대체품이 노출됩니다. 주력 상태와 대체 후보 확인 기록은 같은 트랜잭션에서 저장합니다. 후보가 없으면 `FALLBACK_FAILED`를 남기고 다음 상품을 점검합니다. 정상 상태로 복구되면 기존 주력품을 다시 사용할 수 있습니다.

승인 여부를 담는 `isActive`는 운영자가 관리합니다. 배치가 승인 전 상품을 활성화하거나 기존 `OUT_OF_STOCK`·`DISCONTINUED` 결정을 덮어쓰지 않습니다. 헤더 점검이 지속적으로 403이면 차단과 판매 중단을 구분할 수 없어 수동 확인으로 기록합니다. HTTP 200으로 제공되는 품절 화면은 상태 코드만으로 식별할 수 없습니다. 이미 카탈로그에 등록된 품절 상태는 대체 전환에 반영됩니다. 감사 로그에는 관측된 HTTP 상태, 시간, 전환 결과와 쿼리 문자열을 뺀 URL을 남깁니다.

## 검증

단위 테스트는 16개 코드의 주력/대체 매핑·주의 성분 배제·링크 허용 목록·개인 식별자 제외·사설 DNS·리다이렉트 제한과 5초 중단을 검사합니다. 실제 로컬 Postgres 테스트는 회원/게스트 소유권, 철회된 인증, 원자적 클릭 기록, 302/대체 이동, 오류 복구, 동시 생성, 링크 실패·복구와 승인된 대체 상품 전환를 검사합니다. 50개 동시 warm 추천 API의 P95<300ms를 로컬에서 검증하며 운영 네트워크/SLA 측정은 아닙니다.

브라우저는 320px·1280px 카드/탭 키보드/44px 버튼/접근성·구매처 중계·오류 재시도·빈 상태를 검사합니다. 판매처 응답은 모의 HTML이며 실제 상품/제휴사로 요청하지 않았습니다. 실제 모바일 스크린리더와 실서비스 제휴 전환·정산은 검증하지 않았습니다.

## 피부 타입 쇼핑 화면 확장

사용자 요청에 따라 `/catalog/products`를 두 열 상품 그리드, 전체/4개 카테고리, 상품·브랜드·성분 검색, 성분 필터, 주력·대체순/상품명순 정렬과 네이티브 상품 상세 대화상자로 확장했습니다. 상세는 Escape·닫기·배경 클릭으로 닫고 원래 버튼으로 포커스를 돌려줍니다. 실제 가격이 없어 가격순·할인율·평점·적합도 백분율을 만들지 않습니다. 실제 구매는 기존 제휴 판매처 302 중계만 지원하며 장바구니·인앱 결제는 추가하지 않았습니다.

리포트 ID 없이 진입해도 검증된 본인 회원/게스트의 최신 완료 리포트가 있으면 자동으로 연결합니다. 서버/인증 오류를 가상 추천으로 감추지 않고 기존 오류·재시도 흐름으로 처리합니다. 실제 리포트 화면에서는 피부 타입을 임의 변경하지 않습니다.

본인 리포트가 **없는** 경우에는 명시적인 쇼핑 화면 체험을 제공합니다. 16개 예시 타입 선택은 브라우저의 일시적 상태일 뿐 개인 진단·사진·리포트 기록을 만들거나 수정하지 않습니다. 상품과 브랜드·성분 구성은 가상이며 가격·평점·실제 구매 링크가 없습니다. 상품 그림은 자체 작성한 가상 패키지 일러스트이며 실제 상품 사진이 아닙니다. 실상품의 승인된 이미지가 없을 때는 준비 중 아이콘을 사용합니다. 체험용 데이터는 진단 또는 제휴 API로 전송하지 않습니다.

타입·검색·필터를 바꾸거나 상세를 열어도 카탈로그 API 호출이 없고 새로고침하면 선택이 초기화됨을 브라우저로 확인합니다. 실제 회원의 리포트 자동 연결, 실제 추천 카드의 모의 판매처 이동·품절 대체, 모바일 320px와 데스크톱 1280px 리플로우·접근성도 검사합니다. 운영 DB 추가 변경 없이 체험 모드로 공개할 수 있도록 실제 추천·구매 API를 기본 잠금 상태로 구성했습니다.

## 체험 모드 공개 배포

`CATALOG_LIVE_ENABLED`를 설정하지 않거나 `0`이면 쇼핑 체험만 제공합니다. 실제 추천 API는 `503 CATALOG_PREVIEW_ONLY`, 실제 구매 중계는 내부 준비 안내 화면으로 이동하며 새 카탈로그 테이블을 읽거나 쓰지 않습니다. 이 상태에서는 리포트 쿼리나 로그인 상태와 관계없이 가상 상품임을 표시하고 개인 리포트와 연결하지 않습니다.

실제 모드를 켜려면 운영 migration5·6, 검증된 상품·전성분·제휴 URL과 허용 판매처 등록을 완료한 뒤 서버 환경 `CATALOG_LIVE_ENABLED=1`을 설정해야 합니다. 호스트나 키 값을 브라우저에 넣지 않습니다. 테스트 러너의 웹서버만 실제 엔진 fixture 검사를 위해 이 값을 1로 설정합니다.

공개 배포 전 최초 4개 마이그레이션만 적용한 일회성 로컬 DB에서 새 테이블·컬럼이 없음을 확인하고 회원/비회원의 홈·진단·스냅샷·쇼핑이 모두 HTTP200인지 검사했습니다. 실제 추천·구매 API도 이 스키마에서 안전하게 차단됨을 확인했습니다. 검사 후 생성한 로컬 DB만 제거했으며 운영 DB에는 접속하지 않았습니다.

## 피부 특성과 관심 고민

쇼핑 체험의 피부 특성은 건성·지성·복합성을 지원합니다. 복합성은 별도 브라우저 탐색 조건이며 기존 바우만 16개 코드를 변경하거나 진단 결과로 저장하지 않습니다. 복합성 선택 시 기존 O/D 예시 코드 선택은 숨겨 서로 다른 의미를 혼동하지 않도록 합니다.

색소 관련 표기는 P=‘색소침착 고민’, N=‘색소침착 고민 적음’으로 정리해 홈 리포트에도 적용했습니다. N을 색소침착이 있는 상태로 뒤집지 않습니다. 관심 고민의 색소침착·모공 버튼은 성분 태그를 기준으로 현재 상품을 좁히며 여러 고민 선택 시 모두 만족하는 상품만 표시합니다. 체험 상품 구성·성분 연관 규칙은 가상 예시이며 실제 모공/색소침착 측정이나 효능 보장이 아닙니다. 실상품은 기존 리포트의 주의 성분 제외 결과 안에서만 필터링합니다.

쇼핑 선택지·리포트와 홈 요약에서는 바우만 영문 코드를 표시하지 않고 한글 피부 설명만 제공합니다. 기존 저장 코드와 추천 매핑은 내부에서 유지합니다. 관심 고민에 트러블을 추가했으며, 다른 고민과 함께 선택하면 교집합의 성분 태그를 포함한 상품만 표시합니다. 트러블 필터는 질환 진단이나 치료 추천이 아닙니다.
